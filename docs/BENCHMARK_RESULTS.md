## 결론

100건 규모에서는 LCS가 30배 이상 빠르고 구조도 단순하므로 검색 엔진을 둘 이유가 없다. 1만 건에서 두 방식의 지연시간이 교차하고, 10만 건부터는 역색인이 한 자릿수 ms를 유지하는 동안 LCS는 수십 ms에서 수 초로 늘어난다. 1천만 건에서 전수 탐색 한 번이 7초면 온라인 검색으로 쓸 수 없다. n-gram 역색인은 1천만 건에서도 p95 80ms 안팎을 유지하며 Top-5 97.7%를 달성했다.

정확도는 규모가 커질수록 두 방식 모두 떨어졌다(Elasticsearch Top-1 98.9% → 90.7%, LCS 100% → 79%). 운영 적용 시에는 n-gram 후보 검색 뒤 상위 후보에 LCS나 도메인 규칙을 적용하는 **2단계 재순위**가 다음 개선 대상이다.

## Python 첫 버전과의 차이

첫 버전은 Python으로 작성했고 그 결과는 [`results/archive-python/`](../results/archive-python/)에 남겨 두었다. Python 기준선은 1천만 건 LCS 한 질의에 약 16분(965,045.68ms)이 걸려 1질의만 완주할 수 있었고, 교차점이 100건과 1만 건 사이로 나왔다. 인터프리터 이중 루프와 질의마다 alias를 다시 정규화하던 구현 탓이다. Java로 다시 쓴 뒤 LCS는 약 130배 빨라졌고, 교차점은 1만 건 근처로 옮겨 갔다. Elasticsearch 쪽 수치는 클라이언트 언어와 무관하게 비슷했다. 두 언어의 결과를 섞어 비교하지 않는다.

## 재현성과 한계

- 모든 주소는 seed `20260917`로 생성한 합성 데이터이며 실제 개인정보를 포함하지 않는다. Java `java.util.Random`을 쓰므로 Python 버전과는 데이터가 다르다.
- 주소 ID별 고유 지번을 보장해 서로 다른 정답이 동일 문자열을 갖는 충돌을 제거했다.
- LCS 기준선은 적재 시 alias를 한 번만 정규화한다. 질의마다 정규화하던 Python 버전보다 LCS에 유리한 조건이다.
- 각 조건의 초기 실측 1회 결과다. Elasticsearch p50은 실행마다 2~5ms 사이에서 움직였다(JVM·HTTP 워밍업). 발표용 결과는 동일 조건에서 최소 3회 반복해야 한다.
- 단일 노드 Elasticsearch(2GB heap)와 단일 스레드 Java 기준선의 비교다. 샤드 수, heap, 캐시 상태, 병렬화에 따라 절대값은 달라질 수 있다.
